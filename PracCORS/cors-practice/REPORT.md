# Практическая работа по обеспечению безопасности веб-приложений

## Цель и исходные материалы

Изучить Same-Origin Policy, простые межсайтовые запросы, preflight и настройку CORS. Основа: «Задание на CORS (1).docx» и все текстовые слайды презентации «15-CORS (1).pptx». Особое внимание: механизм (5–12), заголовки (14–24), рекомендации (28), CORS и CSP (29–30).

## Реализация

Приложение 1 работает на http://localhost:8081 и получает `/api/primer1` из приложения 3. Приложение 2 работает на http://localhost:8082 и получает `/api/primer2`. Приложение 3 работает на http://localhost:8083, выполняет фиксированные SELECT-запросы к SQLite и возвращает JSON. Имена таблиц не формируются из произвольного ввода. В каждой таблице три учебные записи.

Параметр `--cors off` воспроизводит исходный этап, `--cors on` добавляет заголовки и проверку origin в приложения 1 и 3. Это два состояния одного проекта, позволяющие сравнить один и тот же запрос и одни и те же данные.

Поскольку основной обмен направлен к приложению 3, CORS в приложении 1 сам по себе не влияет на его исходящие запросы. Для проверки требования «добавьте CORS в приложения 1 и 3» добавлен отдельный `/api/info` в приложении 1, доступный из браузерной страницы приложения 2. Это дополнительный демонстрационный маршрут, а не замена выдачи данных приложением 3.

## Минимальные разрешения

| Сервер и ресурс | Разрешённый origin |
|---|---|
| 8083 /api/primer1 | http://localhost:8081 |
| 8083 /api/primer2 | http://localhost:8082 |
| 8081 /api/info | http://localhost:8082 |

Политика использует точное сравнение, не `*`, подстроку или произвольное отражение Origin. Для preflight разрешены только GET и демонстрационный заголовок X-Lab-Demo. Cookies не используются: fetch задаёт `credentials: 'omit'`, сервер не выдаёт Access-Control-Allow-Credentials. Пользовательские заголовки ответа не нужны, поэтому Expose-Headers отсутствует. Vary учитывает параметры CORS. Кэш preflight отключён для воспроизводимости опыта.

CSP разрешает собственные скрипты и стили и соединения только с собой и двумя серверами, к которым обращается учебный интерфейс. Inline-скриптов, CDN и сторонних библиотек нет. Данные выводятся через textContent. Сетевой доступ ограничен локальным компьютером. Эти меры дополняют CORS.

## Ход опыта и ожидаемые наблюдения

До CORS собственные страницы доступны, SQLite работает: на странице приложения 3 можно прочитать обе таблицы. Но fetch из приложений 1 и 2 пересекает origin, поскольку порт отличается. При простом GET сервер возвращает JSON с HTTP 200, однако браузер не отдаёт этот ответ JavaScript без разрешающего ACAO.

В запросе с X-Lab-Demo браузер сначала отправляет OPTIONS. До CORS в ответе нет разрешений, поэтому основной GET не выполняется. После включения сервер возвращает конкретный ACAO, Allow-Methods: GET и Allow-Headers: X-Lab-Demo, после чего браузер выполняет основной запрос.

После CORS каждый клиент видит свою таблицу. Попытка прочитать чужую таблицу получает от сервера 403 без ACAO. Браузер сообщает ошибку CORS и не позволяет скрипту прочитать даже тело ошибки. Приложение 2 также успешно читает справочное сообщение приложения 1, хотя само приложение 2 не добавляет CORS-заголовки.

Режим no-cors не позволяет получить JSON: ответ opaque, статус для JavaScript равен 0. Это демонстрация ограничения, а не способ решения CORS.

Фактически выполненные проверки и ограничения проверки описаны отдельно в VERIFICATION.md; таблица в README служит сценарием воспроизведения.

## Уточнения к презентации

1. HTTP 403 не обязателен по протоколу CORS. Браузер может скрыть и успешный HTTP 200. В этом проекте 403 — явное решение сервера для запрещённого Origin после включения политики.
2. Origin не доказывает, кто клиент. Внешняя программа может подставить его. Отсутствие Origin допускается для прямого открытия API; такие запросы не проверяются браузерным механизмом CORS. Здесь разграничено чтение в браузере, а не права пользователей в БД.
3. Для Access-Control-Allow-Credentials разрешающее значение — только `true`. Чтобы не разрешать credentials, заголовок опускают; `false` не является разрешающим значением.
4. Не каждый JavaScript-запрос содержит Origin; поведение зависит от контекста и режима. no-cors может использоваться и с допустимым POST, но всегда ограничивает чтение cross-origin ответа. Нельзя использовать отсутствие Origin как доказательство безопасности.

Уточнения сверены с [Fetch Standard WHATWG](https://fetch.spec.whatwg.org/#http-cors-protocol), актуальным на дату выполнения. Они сохраняют основную идею презентации и исправляют упрощения.

## Вывод

Разные порты localhost образуют разные origin. До настройки CORS браузер ограничивал доступ скриптов к ответам приложения 3. После добавления точечных разрешений приложение 1 получает primer1, приложение 2 получает primer2, а запрещённые сочетания остаются недоступны. Отдельный опыт подтвердил работу CORS на приложении 1. Preflight проверяет допустимость сложного запроса до его отправки. CORS следует задавать на сервере, к которому обращаются, и дополнять аутентификацией и авторизацией в реальных системах.

CORS ограничивает браузер, поэтому для настоящей защиты БД потребовалась бы авторизация».

## Вопросы преподавателя

- **Почему один localhost считается разными источниками?** Origin — тройка «схема, хост, порт». Здесь отличаются порты.
- **Почему в Network 200, а на странице ошибка?** Сеть получила ответ, но браузер не передал его скрипту без CORS-разрешения.
- **Почему приложению 2 не нужен CORS?** Оно выступает клиентом. Разрешение добавляет сервер-адресат. По заданию у приложения 2 нет API, который нужно читать с другого origin.
- **Кто отправляет OPTIONS?** Браузер автоматически, когда запрос не удовлетворяет условиям простого запроса; здесь причина — X-Lab-Demo.
- **Почему в Allow-Methods только GET, а OPTIONS работает?** Заголовок перечисляет допустимые методы основного запроса. OPTIONS используется для согласования.
- **Можно ли обойти это через curl?** curl не применяет браузерную Same-Origin Policy. Именно поэтому CORS не является авторизацией.
- **Можно ли разрешить обоим клиентам все маршруты?** Технически да, но это шире требуемой схемы primer1 → приложение 1, primer2 → приложение 2.
- **Зачем CSP?** Она ограничивает источники ресурсов и соединений страницы. CORS задаёт, кто может читать ответ сервера; механизмы решают разные задачи.
